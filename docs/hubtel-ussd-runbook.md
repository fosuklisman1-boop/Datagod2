## 1. Register the service in Hubtel
- Service Interaction URL: `https://<domain>/api/ussd-hubtel/interaction?secret=<HUBTEL_WEBHOOK_SECRET>`
- Service Fulfilment URL:  `https://<domain>/api/ussd-hubtel/fulfillment?secret=<HUBTEL_WEBHOOK_SECRET>`
- Request a USSD code and attach the service on the Merchant Dashboard.
- The app must be on the **apex or canonical host** that serves the API without a redirect (a www/apex redirect broke webhook delivery for Bundle Portal before).
- **Security note:** these URLs carry `?secret=`, and Vercel / proxy request logs may record the query string. If Hubtel can send a custom header, prefer `x-hubtel-secret: <HUBTEL_WEBHOOK_SECRET>` (both endpoints accept it) and drop the query secret.

### PHASE B — production live checks
Phase B **REQUIRES briefly enabling the channel on production**. Safe procedure:
0. **Prove the status-check path BEFORE trusting any expiry decision.** From your machine (export the secret in your shell first, do not type it inline):
   `curl -s -H "Authorization: Bearer $HUBTEL_RELAY_SECRET" "https://relay.<domain>/status?clientReference=<SessionId>"`
   using the SessionId of a known paid session (or of the owner's test session after step 3). Expect `{"ok":true,"upstreamStatus":200,"body":{...,"data":{...,"status":"Paid"}}}` (or `"Unpaid"` for an abandoned session). This proves the Hubtel Basic-auth credentials, the whitelisted relay IP, and the response shape (`body.data.status`) the status-check cron depends on. `ok:false`/`upstreamStatus` 401/403 means credentials or IP whitelisting are wrong; a 200 without `data.status` means the response shape differs from what the code reads — STOP and fix before going live.
   Note: when the final status check at expiry cannot determine the status (relay down, 401, IP not whitelisted, timeout, unexpected shape), the row is NOT expired: it lands in `needs_review` with `callback_last_error` starting "status check indeterminate at expiry". A burst of these means this path is broken.
1. Enable only after Phase A passes and the three env vars (`HUBTEL_WEBHOOK_SECRET`, `HUBTEL_RELAY_URL`, `HUBTEL_RELAY_SECRET`) are set to real values. Enable via `/admin/ussd-hubtel` → toggle **Hubtel USSD enabled**.
2. Attach the Hubtel code to a test/restricted audience, or ensure the owner is the only caller during the window.
3. Make exactly ONE small owner-made purchase (e.g. GHS 1).
4. Inspect the row on `/admin/ussd-hubtel`: state `fulfilled`, `callback_status=sent`, amounts match, no `needs_review`; order completed and SMS received.
5. If ANYTHING looks wrong, toggle the channel OFF immediately (always allowed server-side) and do not re-enable until fixed.
6. **Plan 2 services:** after the data purchase passes, make ONE small owner purchase per service and check the row on `/admin/ussd-hubtel` (state `fulfilled`, `callback_status=sent`, amounts match) plus the service's own record: airtime received (or the manual-airtime admin SMS if Digiwapy is off); results-checker PIN SMS received; check-results request listed on `/admin/results-check-requests` (the owner's number must be a registered Datagod account); AFA order `payment_status=completed` with `fulfillment_status` `fulfilled` or `pending` (the owner must dial from an MTN line). Turn any service you cannot verify OFF in the visibility toggles before widening the audience.

7. **Shop mode (only if the code will run in shop mode):** first confirm Redis is configured in production (otherwise every shop code is refused). With your OWN test shop, make ONE small owner-made purchase per shop service you will offer (data, airtime, vouchers) and check: the row on `/admin/ussd-hubtel` (state `fulfilled`, `callback_status=sent`); the shop's `token_balance` dropped by exactly 1 for that call; `shop_profits` has exactly one row per shop for the order. ## 4. Operate
- `needs_review` rows: fulfil manually (existing `/admin/orders` manual fulfilment). `/admin/refunds` has NO Hubtel support: if the customer was charged but the service cannot be delivered, arrange the refund with Hubtel directly. The callback is still sent as `success` (policy: always success). Each `needs_review` row shows its **reason** under the state badge on `/admin/ussd-hubtel` (`review_reason`, migration `0108`; a short sanitised text such as "underpaid: after_charges X < expected Y", "no handler for order table ...", "late success after expiry", "late success after indeterminate park", the order handler's error message, or the sweep / indeterminate-expiry texts below). Rows parked before `0108` was applied have no reason: check the server log for the session id. A row lands here for:
  - under-payment (`AmountAfterCharges` below the expected amount);
  - a failing order handler;
  - a non-payable order (e.g. the order had already failed);
  - **an expired airtime / results-checker order paid late**: the `expire-stale-airtime` cron (`app/api/cron/expire-stale-airtime/route.ts`, 30-minute cutoff) sets `airtime_orders` and `results_checker_orders` still `pending_payment` to `expired` (not `failed`), which includes Hubtel-created ones. The Hubtel status-check keeps watching the session for up to 60 minutes, so a payment confirmed between 30 and 60 minutes after the order lands in `needs_review` BY DESIGN: the handler refuses the no-longer-payable order and an admin delivers manually (airtime or vouchers). Loud, not silent: the customer paid, so deliver or refund. (`results_check_requests` and `ussd_afa_orders` are not touched by that cron.);
  - **results-checker vouchers out of stock after payment** (`results_checker_orders` paid, `status=pending`): deliver the vouchers manually, then Mark resolved;
  - **a combo "Check Results" request paid with no voucher left** (`results_check_requests`, `mode=combo`, paid, no `voucher_pin`): assign a voucher to the request on `/admin/results-check-requests`, then Mark resolved. The same state is raised if the request did not reach `paid` after fulfilment;
  - **an AFA provider submission failure**: the library records the outcome in `ussd_afa_orders.fulfillment_status`; when it is `failed`/`unfulfilled` (anything other than `fulfilled` or `pending`) the row goes to `needs_review` and the payer is NOT sent the "registration received" SMS. There is no separate AFA retry queue for `ussd_afa_orders`: re-submit or register manually with the provider, then Mark resolved. (`fulfilled` = Sykes accepted; `pending` = Apex Prime accepted, confirmed later by the AFA sync cron.);
  - **a shop-scoped AFA row** (should never happen: neither the main menu nor the shop menu creates one): handle manually;
  - **shop orders (shop mode):** see "Shop `needs_review` reasons" below;
  - a stale `processing` row (stuck >10 minutes, swept by the status-check cron; `callback_last_error` says "recovered from stale processing" and the reason says "handler did not finish (crash/timeout after payment was recorded): ..."). The Hubtel order id and `paid_at` were saved before the handler ran, so the callback can still be sent. The handler may have stopped anywhere: check the order's payment status, the shop / parent-shop profit rows and the fulfilment before resolving;
  - an **indeterminate status check at expiry** (`callback_status=not_due`, reason and `callback_last_error` "status check indeterminate at expiry: ..."): we could not ask Hubtel whether the customer paid. Check the transaction on the Hubtel dashboard (or the relay `/status` call above): if paid, fulfil manually; if not, mark the order failed. The status-check cron re-checks these rows every ~5 minutes, but they usually arrive with ~6 status-check attempts already used and re-checking stops at 12 total attempts, so automatic re-checks cover only roughly the first 30-40 minutes after expiry (never more than 24h). A relay outage longer than that window leaves the row parked until Hubtel's late webhook arrives or an admin resolves it. If Hubtel's success webhook arrives or a re-check says Paid, the payment is recorded and the callback becomes due automatically (`callback_status=pending`), but the order is still NOT auto-fulfilled;
  - a **late payment**: Hubtel reports a successful payment for a session we had already expired (state `failed`, never paid). The customer was told it failed; an admin must fulfil or refund manually — it is never auto-fulfilled.
- Status-check cron (every 2 min): processes up to 50 awaiting-payment rows per run, oldest first; sweeps `processing` rows older than 10 minutes into `needs_review`; makes one final status check before expiring an unpaid row, and expires only when Hubtel definitely says not paid (otherwise `needs_review`). Both Hubtel crons stop starting new rows after ~4 minutes (maxDuration 300s); the next run continues.
- Clearing a worked `needs_review` row: use **Mark resolved** on `/admin/ussd-hubtel` (only offered on `needs_review` rows). A note of 5-500 characters is required; it is stored on the row (`resolution_note`, `resolved_by`, `resolved_at`) and in `admin_audit_log` (`hubtel_resolve_needs_review`). Two outcomes:
  - **Fulfilled** (the goods/service were delivered to the customer manually): row becomes `fulfilled`. If the row has no callback due yet (`callback_status=not_due`) and a Hubtel order id is on record, the success callback is queued (`pending`, window bounded from now) and the callbacks cron sends it. If there is no Hubtel order id, no callback can be sent (the result says so); if Hubtel's success webhook (or a status check) arrives later for that row, the OrderId, amounts and `paid_at` are recorded, the row stays `fulfilled`, the callback becomes due, and the order handler is NOT run again. If a callback was already pending/failed/sent it is left as is (use Retry callback if needed).
  - **Not paid** (`not_paid`, Hubtel never took the payment): only enabled for rows with NO recorded payment (`paid_at` empty) AND no callback due (`callback_status=not_due`), i.e. the indeterminate-expiry rows you have verified as unpaid on the Hubtel dashboard. The row becomes `failed`, no callback is sent, and the linked order is failed exactly like an expiry (only if it is still unpaid; a paid order is never touched). If the order row could not be marked failed (DB error, or it was no longer unpaid) the resolution is still recorded but the result carries a **warning** (shown in the toast and stored in the audit log): the order may still be payable, so check it. A later Hubtel success webhook still recovers the row: the payment is recorded, the row returns to `needs_review` with the callback due, and an admin must fulfil it (or arrange a refund with Hubtel). It is never auto-fulfilled.
  - **Resolution does not change the order row** (except the `not_paid` fail above): after Mark resolved the underlying order (`airtime_orders`, `ussd_afa_orders`, `results_checker_orders`, `results_check_requests`, `ussd_orders`) keeps its previous status. Revenue and order pages that filter on `payment_status=completed` will therefore not count a manually fulfilled order; if reporting matters, update the order row by hand.
  - A row that changed while you were resolving it (late webhook, second admin) is refused with a conflict; reload and retry.
- `/admin/ussd-hubtel` always lists every `needs_review` / callback-failed row (plus the 50 most recent); use the "Needs attention" filter. Session, order and Hubtel order ids are shown short — hover for the full value, click to copy.
- Airtime: paid airtime goes to Digiwapy when enabled for the network, otherwise admins get the manual-airtime SMS (same as Uzo). Check-results requests are worked on `/admin/results-check-requests`. AFA registrations follow the normal AFA provider/sync flow once submitted successfully.
- **Shop mode billing:** one session token per (Hubtel `SessionId`, shop code), billed when the code is accepted via a Redis `SET NX` marker (`ussd-hubtel:shop-billed:<SessionId>:<shopCodeId>`, 1 hour TTL) taken BEFORE the deduction. It is NEVER refunded when the caller cancels, times out or never pays. A redelivered request or a "Session expired" restart of the same Hubtel session never takes a second token; entering a different shop's code in the same session charges that shop. Failure rules:
  - **Production without Redis configured: the code is REFUSED** ("Shop unavailable. Try again.", nothing charged); same during a Redis outage.
  - The marker is released only when the deduction definitely did not happen (balance already 0, or the deduct RPC returned false: "Shop has no sessions left."). If the deduct RPC ERRORS (timeout, 5xx) the marker is KEPT and the code refused: the deduction may have committed, so the worst case is one free session, never a double charge.
  - The shop owner gets the low-token alert when a deduction leaves exactly 10 sessions (Uzo rule).
- **Shop profit:** credited once per order, after payment. Data orders: by the Hubtel handler (`shop_profits.ussd_shop_order_id`, shop margin + parent shop margin from the order's `profit_amount` / `parent_profit_amount`). Airtime and vouchers: by the shared libraries (`airtime_order_id` / `results_checker_order_id`, from `merchant_commission`). A duplicate Hubtel delivery never credits twice (single claim per order on `hubtel_transactions`), and once migration `0108` is applied `shop_profits` also has a unique key per (order, shop) for `ussd_shop_order_id`, `results_checker_order_id` and `airtime_order_id` rows. The handlers verify the credit: data orders check their own inserts (a unique violation is accepted only when the existing row has the expected amount); vouchers and airtime re-read `shop_profits` after the library ran and flag a missing commission. A crash between the "mark paid" step and the profit credit can still LOSE a credit: before the handler claims the payment the tx row stays `awaiting_payment` (the status check picks it up); after the claim it stays `processing` and the sweep moves it to `needs_review` after 10 minutes with the "handler did not finish" reason. In that case reconcile `shop_profits` against the order before resolving.
- **Shop `needs_review` reasons** (shown on the row): "shop profit not credited" / "parent shop profit not credited" (the `shop_profits` insert failed: insert the missing row by hand with the order's `profit_amount` / `parent_profit_amount`, then Mark resolved); "already credited with a different amount" / "existing credit could not be verified" (a row for this order and shop already exists: compare it with the order's amounts and correct by hand); "parent shop is the shop itself" (bad shop data: the parent credit was skipped; fix the shop's parent link and credit by hand if owed); "fulfilment could not be triggered" (the order was left `pending`: fulfil it from the manual queue, then Mark resolved); "vouchers delivered but shop commission not found in shop_profits" and "airtime paid but shop commission not found in shop_profits" (the library's commission insert failed; for vouchers see the fallback-row warning below; airtime has no fallback row: insert the `shop_profits` row with `airtime_order_id` and the order's `merchant_commission`); "status '...' after fulfilment (vouchers sent)" (the voucher library did not record `completed`: set the order `completed` by hand so the expiry cron cannot expire it). The reason is truncated at ~200 characters; the full text is in the server log for the session id.
- **Shop vouchers out of stock after payment (D14):** the row goes to `needs_review` ("paid but out of stock"), the order stays `pending`. The admin must deliver the vouchers AND credit the shop its `merchant_commission` by hand, because the library only credits it on automatic delivery; then Mark resolved. **Double-credit warning:** the results-checker library, if its linked `shop_profits` insert fails, inserts an UN-LINKED fallback row (same `shop_id` and amount, no `results_checker_order_id`). Before crediting by hand, query `shop_profits` for a row with the same `shop_id` and amount and no order link created around the order's time (and for any row with this `results_checker_order_id`); if one exists the shop was already credited: link/keep it instead of inserting another. The same check applies to the "commission not found" reason above.
- **Late payment on a shop order** (paid after the order expired): the row lands in `needs_review`; the order stays failed, no profit is credited and nothing is delivered. Deliver (and credit profit) or refund manually.
- **Mode switching:** the Mode on `/admin/ussd-hubtel` applies to NEW dials; an in-flight session keeps the mode it started with (pinned in the session), and a Response with no session restarts in the current mode. The kill switch beats pinning: disabling the channel releases in-flight sessions of either mode ("Service unavailable"). A paid cart replays correctly even if the Mode flipped meanwhile.
- Callbacks cron (every minute) retries pending callbacks.
- `callback_failed`: Retry callback button (re-arms a fresh window; Hubtel may reject after 1 hour).
- Rollback: toggle the channel OFF; Uzo codes are unaffected.

## 5. Known limitations (after Plan 3)
- Shop mode is built and selectable (Mode on `/admin/ussd-hubtel`). It serves one shop per call through its shop code and offers data, airtime and results-checker vouchers only: no AFA, no "My Vouchers", no "Check Results" (same as the Uzo shop code). Shop orders use `channel='ussd_shop'` like Uzo shop orders; join `hubtel_transactions (order_table, order_id)` to tell Hubtel ones apart. In shop mode "0" on the network menu returns to the shop's menu (the Uzo shop code returns to code entry); to use another shop, redial.
- What remains open after Plan 3: `dialing_phone` is stored E.164 (`+233...`) while Uzo stores the raw msisdn (affects Uzo shop "my orders"/pending-OTP lookups and the `/admin/refunds` payer phone); no `payment_attempts` rows are created for Hubtel orders; the shared libraries `fulfillUssdOrder` / `customerTrackingService` log recipient phone numbers (PII in logs, kept for parity with Paystack/Uzo); a concurrent duplicate delivery of a shop code may get one free session; callback double-send idempotency still has to be confirmed with Hubtel; migration `0108` (shop-profit unique keys + `review_reason`) is written but NOT applied (see section 0); the live visual check of `/admin/ussd-hubtel` and the live simulator runs (Phase A, incl. `SHOP=1`) have not been done.
- Check Results requires a registered Datagod account (same rule as the Uzo code). AFA is only offered to MTN callers.
- Own-voucher check requests are charged the check fee rounded to 2 decimals; the combo is the single-voucher price plus the fee (no bulk pricing).
- Hubtel orders use `channel='ussd'` like Uzo orders; to report Hubtel separately, join `hubtel_transactions (order_table, order_id)`.
- The status-check cron handles at most 50 awaiting rows per run (oldest first); a large backlog drains over several runs.
