# Developer API v2 — Design

Date: 2026-10-22. Status: draft for approval. Extends (does not replace) `2026-09-15-developer-api-page-design.md`, which covers the v1 expansion and in-app developer page.

## Intent

Datagod's public developer API (`/api/v1`, `dg_live_`/`dg_test_` keys) is a single-key-type API with flat string errors, one per-key rate number, no key approval and thin admin tooling. The user wants it rebuilt to match the structure of the competitor reference at https://kingflexygh.com/developers (their "Developer API v2" and its admin API-key console), using Datagod naming. Reason (the user's words): "We going to rebuild our api … Same as this site"; "The admin side too will have these exact features"; "The public page will use postman collection plus Flexy style".

Three deliverables:
1. **`/api/v2`**, a new API living beside v1, covering every product group.
2. **Admin API-key console** (rebuild of `app/admin/api-keys`) with the Flexy-style features.
3. **Public `/developers` docs page** plus a Postman collection.

## Decisions made by the user

- v2 lives beside v1. **v1 stays untouched and keeps working** for current developers; retirement is a later, separate decision. The admin console manages both v1 and v2 keys.
- **Same shape as the reference, Datagod naming** (not drop-in compatible). Same endpoint groups, response envelope, key types, error codes and rate-limit structure; Datagod prefixes, field names where Datagod's differ, and Datagod branding.
- **Scope: everything**, all four groups at launch: data/wallet/orders, airtime/utility bills, results checker/AFA, SMS.
- **Base URL on an `api.` subdomain from day one** (production domain is `datagod.store`, so `https://api.datagod.store/v2/...`). No DNS or Vercel domain work is needed (checked 2026-10-22): `*.datagod.store` is already on the Vercel project with a wildcard ALIAS, `api.datagod.store` already resolves, and `middleware.ts` already reserves the `api` label so it is never treated as a shop subdomain. What remains is code: a host-based rewrite in `middleware.ts` mapping `api.datagod.store/v2/*` to `/api/v2/*`, and making the `api.` host serve only API routes (not the main site). The path form `https://www.datagod.store/api/v2/...` should keep working as the underlying route.
- **Public page: layout A.** One long page with a sticky side navigation (Start / Data / Commission / Results & AFA / SMS / Sandbox), each endpoint documented with request, response and errors, and a "Download Postman collection" button. Content mirrors the reference page.
- The public page must offer a **Postman collection** (downloadable, covering every v2 endpoint, with a key variable and base-URL variable). Approach (my call): a Postman Collection v2.1 JSON file plus a sandbox and a live environment file, served as static downloads from the site (e.g. under `public/developers/`) and linked from the page's "Download Postman collection" button. They are generated by a script from the same endpoint registry that renders the docs page, so the page and the collection cannot drift apart, and a test fails if an endpoint is in one and not the other. A one-click "Run in Postman" button would need a public Postman workspace and is a later nice-to-have, not part of this project.

## Reference behaviour to reproduce (from the reference page)

**Key types.** Each type works only with its own endpoint group; the wrong type returns 403.
- Standard: data, wallet, orders, results checker, AFA.
- Commission Services: airtime, utility bills.
- SMS: SMS endpoints (generated separately from the SMS dashboard).

**Response envelope.** Success: `{ success: true, data: {...}, meta: { timestamp, version } }`. Error: `{ success: false, error: { code: <number>, message } }`.

**Error codes.** 400 bad input or insufficient wallet; 401 missing/invalid key; 402 insufficient SMS credits; 403 wrong key type, pending/revoked key, suspended account or role not allowed; 404 not found; 409 duplicate reference or duplicate payment (also unregistered MTN number on data purchase); 429 rate limit; 500 internal; 502 upstream unreachable (verification/lookup); 503 feature or biller disabled by an admin.

**Idempotency.** Every purchase takes a `reference`. Reusing it with the same request returns the existing order with no new charge; reusing it for a different order returns 409. Utility payments return the original order on reuse even if other values changed. AFA references are unique across all developers.

**Endpoints (reference, to be mapped onto Datagod's products):**
- Standard key: `GET /packages` (filters network, size); `POST /data/purchase`; `POST /data/bulk` (up to 100, whole batch rejected on validation failure with no charge, unregistered MTN recipients skipped individually and listed); `POST /data/verify-number` plus per-server variants; `GET /wallet/balance`; `GET /orders/{reference}`; `GET /account/role`; results checker (`types`, `purchase`, `orders`, `orders/{reference}`); AFA (`register`, `orders`, `orders/{reference}`; 18+, Ghana Card, 16 regions).
- Commission key: `POST /airtime/purchase`, `GET /airtime/orders`, `GET /airtime/orders/{reference}`; utilities (`billers`, `lookup`, `pay`, `orders/{reference}`) for ecg, ghana_water, dstv, gotv, startimes.
- SMS key: `POST /sms/send` (up to 10,000 recipients, immediate at ≤500 else queued), `GET /sms/senders`, `GET /sms/messages/{campaignId}`, `GET /sms/campaigns`, `GET /sms/balance`. SMS credits are separate from the GHS wallet.

**Rate limits (reference):** purchases 10/min, list/status calls 30/min, verification 20/min (shared), utilities pay 6/min, lookup 10/min. Datagod's numbers are the builder's call, set per endpoint group, with admin per-key overrides.

**Key lifecycle.** Generated from the dashboard (allowed roles only), shown once, created as pending, active after admin approval; generating a replacement revokes the old one; revoke is a disable, not a delete. No webhooks in the reference: status is by polling order endpoints.

## Admin console (rebuild of `app/admin/api-keys`)

Screens seen in the user's screenshots of the reference admin:
- **Overview tiles:** total keys, pending, active, requests (24h), revenue (24h with lifetime), success rate (24h), failed (24h), average latency, and a "top API user (24h)" card.
- **Feature controls:** global "API access enabled" switch, and an **allowed-roles** selector (agent, dealer, subagent, customer, sub-admin, admin) saying which roles can generate and use keys. Applies immediately to new requests.
- **Tabs:** API Keys and Request Logs.
- **Key list:** search (name, email, phone, key prefix); filter by All/Pending/Active/Revoked and by role; sort. Each row: owner, masked key prefix, status, key-type badge (Standard / Commission · Utilities / SMS), role, requests in 24h, last used. Actions: Approve (pending), Revoke, an expandable **User Activity** panel (spent, orders, success, failed, pending, success rate, 24h requests, average latency) and a **Per-Key Rate Limits** editor (purchase, bulk, balance, status; req/min) with Save and Reset to Default.
- Manages v1 and v2 keys in one place (my call: show v1 keys with a "v1" badge; approval/key-type/limit-group controls apply to v2 keys only).

## Public `/developers` page: required detail and polish

The user's instruction (verbatim): "Much deatails and should be professional", with two screenshots of the reference's Authentication and Endpoints sections. The page is a full reference, not a summary. Every endpoint is documented to the depth shown below, and the finish must look professional in both light and dark, on mobile and desktop (layout A: sticky side nav on desktop; on mobile a sticky "Section: <name>" bar with a "Contents" button that opens the section list).

**Authentication section** (as in the reference): explains the `Authorization` header with a copyable example; a prominent warning callout that the key is shown only once and that generating a new one revokes the old; a numbered "Getting your API key" list (log in with an allowed role, open Dashboard → Developer API, generate and accept the policy, copy and store the key, wait for admin approval: pending → active). Also covers key types and which endpoint groups each unlocks, sandbox keys, and the `X-API-Key` alternative.

**Each endpoint** gets: method + path + one-line purpose, which key type it needs, rate limit, parameter table (name, type, required, description, constraints), a full example request and a full example success response (real shape, `success`/`data`/`meta`), the endpoint-specific error responses, and a short notes list (role-specific pricing, availability filters, idempotency behaviour, when to call it) styled like the reference's arrow-bullet callout.

**Code samples** per endpoint in **cURL, Node.js, PHP and Python** (tabbed), each with a Copy button, long lines scrolling horizontally and never clipped. Samples use the real v2 base URL and a placeholder key. They are generated from the same endpoint registry as the Postman collection so docs, samples and collection cannot disagree.

**Reference sections**: response format, full error-code table, rate limits table, idempotency rules, order status lifecycles per product (e.g. pending, queued, processing, completed, failed, refunded), sandbox behaviour and test values, support contact for limit increases.

Datagod navy accent, clear typographic hierarchy, consistent callouts (info / warning), no placeholder or lorem text, and the Postman download button visible near the top and in the side nav.

## Datagod facts the builder starts from (as found 2026-10-22)

- v1: 13 routes under `app/api/v1` (bundles, bills, airtime, sms/send, afa, results-checker, balance, orders, products, sandbox reset). Auth in `lib/api-auth.ts` (`X-API-Key`, SHA-256 hashed keys in `user_api_keys`, logging to `user_api_logs`). Sandbox in `lib/sandbox.ts` via `dg_test_` keys. Rate limiting via `lib/rate-limiter.ts` `applyRateLimit`. Standard bundles, Hubtel commission services, SMS platform and results-checker engines already exist in `lib/` and should be reused by v2 rather than reimplemented.
- v1 lets any authenticated user generate keys (per the 2026-09-15 spec); v2 replaces that with the admin-controlled allowed-roles list above.
- Admin today: `app/admin/api-keys/page.tsx` (588 lines), `app/api/admin/api-keys` (list/enable-disable/one rate limit/delete), `api-logs`, `global-kill`. Developer dashboard: `app/dashboard/developer/page.tsx`, `components/developer/DeveloperKeysCard.tsx`, docs registry `lib/api-docs-registry.ts` (`BASE_URL = https://www.datagod.store`).
- No public `/developers` page exists yet.

## Goals

- A developer can integrate any Datagod product through one consistent, documented, safe API.
- Admins can approve, limit, monitor and kill access without database work.
- A Postman collection that works against sandbox out of the box.

## Non-goals

- Not retiring or changing v1 in this project.
- Not drop-in compatibility with kingflexygh's paths or field names.
- No webhooks in this project (the reference has none; flagged as a possible later addition).
- No new products; v2 exposes what Datagod already sells.

## Anti-goals (failure even if it technically works)

- A key of one type reaching another group's endpoints.
- Any path where a developer gets product free, pays twice, pays a cheaper price than their role's, or reaches someone else's orders or keys (abuse-case pass required on every endpoint).
- Unapproved, revoked, or role-disallowed keys working; the global kill switch not stopping v2 immediately.
- Secrets or PII in logs; full keys ever shown after creation.
- v1 consumers broken by shared-table or shared-code changes.

## Constraints

- Follows the Datagod guardrails already recorded for money, auth and schema work: server routes derive the owner from the key (never trust client-supplied user ids), RLS and storage model as per existing grant model, PII-free logs, `verifyAdminAccess` for admin routes, no destructive prod change without the prod-change protocol (precheck, dry run, approval, apply, verify).
- **Money, auth and schema changes require a fresh-eyes review before merge** (project review-gate rule), with failing tests written first and logic in `lib/`.
- Must pass a real `next build` before pushing main.
- New sidebar/admin entries need the NEW tag (`lib/nav-new.ts`).
- Customer/developer UI uses the navy-blue brand accent and works on desktop (multi-column from the start) as well as mobile.
- Ships dark: v2 behind an admin on/off switch, off until the owner enables it.
- Staged delivery. Suggested order (builder may refine): (1) key system, envelope, errors, rate-limit groups, approval, global switch; (2) admin console; (3) data/wallet/orders; (4) airtime/utility bills; (5) results checker/AFA; (6) SMS; (7) public `/developers` page and Postman collection; (8) `api.` subdomain wiring.

## Calls I made (the user has not decided these)

1. Key prefixes: `dg_live_` (standard), `dg_cs_live_` (commission), `dg_sms_live_` (SMS); test equivalents for sandbox (`dg_test_`, `dg_cs_test_`, `dg_sms_test_`).
2. Sandbox carries over to v2 for all three key types.
3. Auth header: accept `Authorization: <key>` (with or without `Bearer`) and also `X-API-Key`, so v1 habits keep working.
4. v1 keys appear in the new admin console with a "v1" badge and limited controls.
5. v2 launches dark behind an admin switch.
6. Webhooks are out of scope.

7. **Pricing.** v2 charges exactly what v1 and the dashboard charge for the key owner's role. It wraps the existing engines in `lib/` (standard bundles, Hubtel commission services, results checker, AFA, SMS) and adds no pricing or role logic of its own; `GET /account/role` reports the role those engines already resolve.
8. **Key storage.** v1 keys stay in `user_api_keys`, untouched in behaviour. Whether v2 extends that table with additive columns or uses a new table is the builder's call, but nothing may change how a v1 key authenticates. A user can hold one active key per type (Standard, Commission, SMS); generating a replacement revokes only that type's old key.
9. **SMS.** SMS keys are issued only to users who already have an SMS account. API sends go through the existing SMS policy engine, sender-ID approval and KYC exactly as the dashboard does, and use the current provider plumbing and queue. The reference's 10,000-recipient cap and "500 or fewer immediately, else queued" are starting points; the builder adjusts them to what the current engine supports and documents the real limits.
10. **Mapping.** v2 exposes only what Datagod already sells. If a reference feature has no Datagod equivalent (e.g. a second verification server, a utility biller Hubtel doesn't support), it is omitted and the public page does not mention it. Unregistered-MTN handling (409, bulk skipping) uses the existing MTN registry and whitelist logic.
11. **Idempotency.** `reference` is unique per key owner (user), enforced in the database with an atomic claim so concurrent duplicates cannot double charge; AFA references are unique globally. Where it is stored (existing order tables or a dedicated table) is the builder's call.
12. **Switches.** The existing `global-kill` stops v1 and v2 together. The new v2 on/off switch and the allowed-roles list apply to v2 only; v1 behaviour is unchanged.
13. **Sandbox.** Test keys never reach live providers, wallets or real orders. Sandbox calls are logged and rate limited like live ones, and are excluded from the admin revenue and success-rate tiles. The Postman collection ships with a sandbox environment preconfigured.
