# Developer API v2 — Plan 5: Results Checker and AFA Registration (Standard key)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a standard-key developer buy results-checker vouchers (`GET /resultschecker/types`, `POST /resultschecker/purchase`, order list and lookup) and register customers for MTN AFA (`POST /afa/register`, order list and lookup), each with a required client `reference`, claim-before-engine idempotency, sandbox parity and full documentation, by wrapping the existing `purchaseResultsCheckerVouchers` and `submitAfaOrder` engines.

**Architecture:** Same pattern as plan 4. The idempotency claim table `api_v2_idempotency` (live) gets two new kinds (`results`, `afa`) through a tiny migration; v2 writes a claim BEFORE calling the engine, classifies engine errors into no-charge (release the claim) and ambiguous (mark unknown, never re-run), and completes the claim with an allow-listed order. Voucher PINs are NEVER stored in the claim: a replay or lookup re-reads them from `results_checker_inventory` through the owner-scoped order. Decision logic lives in `lib/api-v2/`; routes are thin `withV2` wrappers (`requiredType: "standard"`).

**Tech Stack:** Next.js 15 route handlers, Supabase (service role), Postgres, Vitest (fake-client pattern), the docs registry from plan 2, plan 4's `commission.ts` helpers and `idempotency.ts` store.

**Spec:** `docs/superpowers/specs/2026-10-22-developer-api-v2-design.md`. Prior plans: 1-4 (live, v2 dark). Ledger of plan 4 rulings applies: claim states, own-claim lookup shape `{ order: null, claim: { reference, state } }`, `userId` guards on claim writes, message wording never invites a new reference.

**Risk tier:** Tier 1 (money, PINs that are worth money, PII). Mandatory fresh most-capable-model whole-branch reviewer (if the top model's quota is exhausted when the branch is ready, say so to the user and use the strongest available with extra scrutiny, flagged in the ledger), a database-reviewer pass on the migration, the abuse-case pass, failing tests first, and the prod change protocol (dry-run string built BY CODE that asserts no `COMMIT`/bare `END;`, explicit `BEGIN`, ends in a `SELFTEST_OK` raise; user OK before apply).

## Facts found in the code and prod (2026-10-26)

- `purchaseResultsCheckerVouchers` debits with `deduct_wallet`, then inserts the order, then assigns inventory with an RPC; on missing inventory it credits the wallet back (`credit_wallet_safely`, result unchecked) and throws `INSUFFICIENT_INVENTORY`; on order-insert failure it refunds by writing `balance = balanceBefore` (the same clobber risk as airtime) and throws an UNCODED error. It returns `{ order, vouchers: [{id, pin, serial_number}], newBalance }`. It has no client reference and no dedupe (v1 uses a 30-second look-back on user+board+quantity+pending).
- `submitAfaOrder` validates the Ghana Card (`INVALID_GHANA_CARD`) and price (`PRICE_UNAVAILABLE`) BEFORE any debit, then `deduct_wallet` (`PAYMENT_FAILED` / `INSUFFICIENT_BALANCE`), then inserts `afa_orders` (`ORDER_CREATE_FAILED`, same `balanceBefore` refund). Its order code is `AFA-` + the last 7 digits of `Date.now()` (millisecond clock, not unique-constrained: `afa_orders` has only a primary key on `id`). Fulfillment runs fire-and-forget after the insert (not awaited: can be lost on serverless; existing behaviour). No duplicate guard at all.
- Prod: exam boards `WASSCE`, `BECE`, `NOVDEC`; `results_checker_max_quantity` = 15; prices WASSCE 18, BECE 18, **NOVDEC 1** (looks like a test price: report to the user, do not change); bulk min 8 at 17. `results_checker_orders` statuses: completed, pending_payment, failed. `afa_orders`: completed/fulfilled 293, processing/pending 29 (older), completed/failed 2.
- Datagod's AFA registration collects: full name, phone, Ghana Card number, location, region, optional occupation. It does NOT collect date of birth: the reference API's 18+ rule is omitted (spec call 10: omit what Datagod has no equivalent for).

## Datagod invariants this plan touches (feedback-business-logic-guardrails)

- Prices come from the engine/admin settings; the request carries no price. Admin board switches, max quantity and stock are enforced (handler pre-checks plus engine).
- The account phone gate (`checkPhoneVerified`, fail closed) applies to live purchases/registrations as on v1.
- AFA price comes from `afa_registration_prices` (engine); the Ghana Card is validated before any debit.
- Failed orders are refunded by the existing admin/refund machinery; v2 only reports status.

## Global Constraints

- v1 untouched: no edits to `app/api/v1/**`, `lib/api-auth.ts`, `lib/results-checker-service.ts`, `lib/afa-fulfillment.ts`, existing migrations. v2 may import their exported functions read-only.
- Plans 1-4 rules apply: envelope, key rules (`requiredType: "standard"`; a commission key gets 403), `failClosedWhenLimiterDegraded` on purchase/register, groups `purchase` (purchase and register) and `status` (types, lists, lookups), fixed generic messages with machine codes prefixed in `message` (`REFERENCE_REUSED`, `REQUEST_IN_PROGRESS`, `OUTCOME_UNKNOWN`, `PHONE_NOT_VERIFIED`, `PRICE_CHANGED` where relevant, `DUPLICATE_REGISTRATION`, `OUT_OF_STOCK`), no phone numbers, Ghana Card numbers, PINs, emails or bodies in logs.
- Idempotency (client `reference` REQUIRED, 3-100 chars via `parseReference`): same reference + same request => 200 `{ ..., replayed: true }` with NO second charge and NO second engine call; same reference + different request => 409 `REFERENCE_REUSED`; same reference still running => 409 `REQUEST_IN_PROGRESS`; ambiguous outcome => 409 `OUTCOME_UNKNOWN` (never re-run); claim written before the engine; finalisation guarded by `userId`; `classifyEngineError`-style tables are pure and fail safe (unknown => ambiguous).
- Request hash: sha256 of key-sorted canonical JSON. Results: `{ board, quantity, recipient_phone (local form or null), recipient_email (lowercased or null) }`. AFA: `{ full_name (trimmed, single-spaced, case-preserved), phone (local form), card: sha256(canonical card number), region, location (trimmed), occupation (trimmed or null) }`. Only hashes are stored, never the card number.
- Results claim finalisation: engine success => claim `done` with `order_ref` = the engine `reference_code` and `response` = the allow-listed order WITHOUT vouchers. Replay (`done`) re-reads the order and its vouchers owner-scoped: the response body repeats the vouchers (PINs) exactly as the reference API does, but PINs live only in `results_checker_inventory`.
- Engine classification (derive from the source, same method as plan 4, and list source lines in the report): Results: `INSUFFICIENT_BALANCE` (thrown when `deduct_wallet` returned no rows) => no_charge; the handler's own stock pre-check (`OUT_OF_STOCK`, board disabled, quantity limits) happens BEFORE the claim's engine call and releases the claim; `INSUFFICIENT_INVENTORY` (thrown AFTER a debit and an unchecked refund credit) => AMBIGUOUS; every uncoded error ("Failed to process payment", "Failed to create order. Wallet refunded.") => ambiguous. AFA: `INVALID_GHANA_CARD`, `PRICE_UNAVAILABLE`, `INSUFFICIENT_BALANCE` => no_charge; `PAYMENT_FAILED`, `ORDER_CREATE_FAILED`, uncoded/unknown => ambiguous.
- AFA duplicate guard (v2-only, new): before the engine call, if this user already has an `afa_orders` row with the same normalised phone OR the same Ghana Card number, status not `failed`, created in the last 10 minutes, answer 409 `DUPLICATE_REGISTRATION` (claim released) so a timeout-then-new-reference retry cannot register and charge twice. Owner-scoped query; no card numbers in the message.
- Public order objects (allow-lists; numbers rounded to 2 dp): Results `{ reference, exam_board, quantity, unit_price, total_paid, status, created_at }` plus a separate `vouchers: [{ pin, serial_number }]` on purchase/replay/lookup; AFA `{ reference, full_name, phone, region, amount, status, created_at }` (no Ghana Card, no location text beyond region, no internal ids). `reference` is the CLIENT reference; the engine `reference_code` / `order_code` is stored only as the claim `order_ref`. Status mapping DB -> API: `completed` -> `completed`, `pending`/`pending_payment` -> `pending`, `processing` -> `processing`, `failed` -> `failed`, `refunded` -> `refunded`, anything else -> `processing`; AFA additionally maps `fulfillment_status` `failed` on a `completed` row to `failed`? NO: keep `status` authoritative and expose `fulfillment_status` mapped to `fulfillment: "fulfilled" | "pending" | "failed"` (unknown => "pending").
- Sandbox (`test` keys): same parsing and pricing reads, replay by client reference via `getSandboxOrder`, then `placeSandboxOrder` with `apiV2KeyId` (actions `results_checker` and `afa`); sandbox results return fake PINs with the clear prefix `TEST-` and fake serials; never calls the engines, claims, gates, inventory or providers.
- Edit with Edit/Write tools, never `sed`. Real `next build` before pushing main. Work only in the clean worktree. Unique test phones per file.

## Review Focus

- PIN handling: PINs never in logs, claims, errors or the docs examples (examples use obviously fake PINs); replay and lookup are owner-scoped through the order; a foreign reference gets the identical 404; the voucher read cannot return another order's PINs when two orders share a board.
- Two concurrent identical purchases: one engine call; two different references racing the last N vouchers: the engine's atomic assignment decides, the loser gets an ambiguous/refund outcome handled safely.
- `INSUFFICIENT_INVENTORY` after debit: claim becomes `unknown`, urgent admin alert, response OUTCOME_UNKNOWN with the refund-expected wording; never released.
- Quantity: 0, negative, 1.5, "3", 16 (above max 15), 100000, NaN; boards: case variants (`wassce`), `WAEC` (a legacy alias in settings: reject), unknown; recipient phone/email forms; delivery fields only deliver when given (decision below).
- AFA: name edge cases (empty, 1 char, 200 chars, digits, unicode), Ghana Card forms (lowercase, spaces, missing dashes) via `parseGhanaCardNumber`, region list (16 official regions; case/spacing), phone forms, duplicate guard windows (same phone different card; same card different phone; failed order does not block; 11 minutes later does not block), forbidden fields (price, amount, status, user_id, fee...).
- Stock and switches: board disabled => 503 `...unavailable`; stock below quantity => 409 `OUT_OF_STOCK` before any charge; `GET /types` never shows PIN data and shows stock as a number.
- Replay of an order whose delivery SMS failed; replay after the board was later disabled (replay must still answer).
