# API Money Protection (Release 5) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Daily spending caps on live v2 keys (developer per key, admin per person, stricter wins) enforced by an atomic spend ledger, plus deduplicated admin fraud alerts; everything ships dark.

**Architecture:** Migration 0198 adds four service-role tables and SQL functions (reserve, settle, set cap, settings, today, risk scan). The request path calls `reserve` after the claim (commission) or after pricing (data) and `settle` on the outcome, only for live purchases and only while a 10 s settings snapshot says caps are on. A 5-minute cron scans for risk signals, dedups in a table and notifies admins.

**Tech Stack:** Next.js 15 App Router, Supabase Postgres (plpgsql, SECURITY DEFINER), Vitest + PGlite, React (render-to-string tests).

**Spec:** `docs/superpowers/specs/2026-11-24-api-money-r5-design.md`

## Global Constraints

- Branch `feat/api-money-r5`, worktree `B:/worktrees/api-rebuild`; run vitest from the uppercase `B:/` path: `CI=1 npx vitest run <files> --maxWorkers=2`.
- Migration number `0198`; re-check with `git ls-tree` over every ref before Task 1 and before applying. (`0196` belongs to another session's branch.)
- New tables: RLS on, no policies, `REVOKE ALL ... FROM PUBLIC, anon, authenticated`; functions `SECURITY DEFINER`, `SET search_path = public, pg_temp`, EXECUTE to `service_role` only. No ALTER of an existing table.
- Both switches seeded **off**: `caps_enabled = false`, `alerts_enabled = false`. With caps off, the request path makes **no** ledger call.
- Live keys only; test keys never reserve, settle or alert. SMS is never capped.
- Error for a refused purchase: HTTP **402**, message prefix `DAILY_LIMIT_REACHED: ` then `Daily spending limit reached. Try again after 00:00 GMT or raise the limit.`; when the binding scope is `user` (admin), the text adds `A Datagod limit applies.` and never the value.
- Day boundary: UTC date (Ghana is GMT). Amounts `numeric(12,2)`; cap range `> 0` and `<= 1000000`.
- No money engine, `place_api_v2_order`, price or fee changes. Never invent prices; alert thresholds are operational defaults from spec §7.
- Code edits with Edit/Write only (no sed). Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- UI: navy `--primary`, light theme, works at 500 px, `lg:` multi-column; render tests live under `lib/` (vitest only collects `lib/`, `app/`, `components/ai/`).
- Lib files outside `app/admin` must never name the admin cost table (`lib/roles/package-costs.guard.test.ts`).

## Review Focus

1. A burst of parallel purchases on one key (or several keys of one person) must never together exceed the cap: the reserve is serialised per user.
2. A refused-for-cap commission purchase releases its claim, so the same reference works after midnight or a raise; a data purchase refused for cap charges nothing.
3. A replay (same reference, already completed) never reserves again and never releases the original row.
4. Engine throws or an ambiguous outcome after a successful reserve: the row stays `reserved` (counted), never released.
5. The admin cap value never appears in any developer-facing response, page or error.

Each line has its test in the owning task (Tasks 1, 3, 4, 5).
